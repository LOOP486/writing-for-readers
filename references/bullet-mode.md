# 条目模式

## 格式契约

- 只允许主标题使用一级标题 `#`。
- 主标题之后的全部正文都放入无序项目符号中，统一使用连字符 `-`。
- 不使用二级或更低级标题，不使用数字编号，不使用表格，也不让解释性段落游离在项目符号之外。
- 使用两个空格缩进一级，最多使用四级。只有存在真实的包含、解释或因果关系时才增加层级。
- 每个项目表达一个完整意思。优先写成一句清楚的话；需要继续解释时，拆成下一级项目，不在同一项目中塞入一整段。
- 同层项目保持相同抽象层级。概念、例子和结论需要分层时，让上级项目提出概念，下级项目负责解释或举例。

## 组织方法

- 第一个一级项目给出核心判断或目的，使读者不展开全部层级也能理解主题。
- 后续一级项目承担主要章节功能，可以使用加粗短语作节点名，例如 `- **核心问题：**……`。
- 二级项目展开原因、机制、组成部分或行动；三级项目只在需要说明具体条件、例子或后果时使用。
- 顺序流程仍使用项目符号，通过“先、随后、最后”或阶段名称表示时序，不改用数字列表。
- 不为了视觉整齐强行凑相同数量的子项。层级服务于内容关系，不服务于模板对称。

## 句式要求

- 用完整判断代替关键词堆叠。写“资源提交会直接改变地图中的防御设施”，而不是只写“资源提交：地图变化”。
- 让父项能够概括子项，子项能够回答父项中的“为什么、如何或会怎样”。
- 同一句中存在两个可以独立理解的结论时，拆成同层或上下层两个项目。
- 保留必要的第一人称判断，但不写“下面将分点说明”等格式说明。

## 输出骨架

```markdown
# 标题

- **核心判断：**一句话说明全文最重要的结论。
  - 补充这一判断成立的背景或边界。
- **作用机制：**说明对象如何运行。
  - 规则或条件会改变人的选择。
    - 用一个具体例子说明这种变化。
  - 这些选择进一步形成可观察的结果。
- **最终影响：**回到读者关心的问题，说明价值、风险或下一步。
```

## 交付前扫描

- 除一级标题和代码示例外，每一行实质正文都属于某个 `-` 项目。
- 文中没有 `1.`、`2.`、`（一）` 等编号。
- 任一项目即使脱离相邻修饰语也能读懂，没有只剩名词的空壳节点。
- 层级能够被口头复述为“这一点包含这些方面”或“因为这些原因，所以得到这个结论”。
